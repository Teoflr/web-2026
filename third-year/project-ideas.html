Third-Year Project Ideas

Twenty frontend project briefs designed to be completed in approximately 24 hours.

Duration: Approximately 24 hours Stack: React, Vite, React Router, Material UI Data: Public APIs, localStorage, or bundled JSON Backend: Not required
On this page Requirements Local data Public APIs Hybrid projects Git repository Assessment

Project requirements

Build a focused, complete application

Your project should demonstrate the topics from the Year 3 tutorials. Aim for a well-finished application with a clear purpose rather than a large collection of unfinished features.

Technical requirements

  • Three to five routes with React Router, including a useful not-found page.
  • Reusable React components with clear responsibilities and data passed through props.
  • Controlled forms, validation, event handling, and immutable state updates.
  • At least one reusable custom Hook, such as useLocalStorage or useFetch.
  • Context or useReducer for one genuinely shared or complex feature.
  • A responsive Material UI interface with a theme and accessible labels.
  • Loading, empty, success, and error states where they are relevant.

Keep within scope

  • Use no more than one primary public API.
  • Do not add authentication, payments, chat, or a custom backend.
  • Use bundled JSON for read-only starter content and localStorage for data that users create or edit.
  • Do not make every screen configurable. Concentrate on the main user journey.
  • You must be able to explain, test, and adapt all code included in your submission.

Projects using local data

1

Study Planner

Build a personal academic dashboard where a student can organise modules, assignments, revision sessions, and deadlines. The home screen should show what is due soon and calculate progress from completed tasks.

The project is entirely local, keeping the focus on React state and interface design rather than API reliability. Seed data can demonstrate the application on first launch, while changes are saved in localStorage.

  • Create, edit, complete, and delete assignments.
  • Filter work by module, priority, completion state, or deadline.
  • Provide dashboard, module, assignment, and settings routes.
  • Show overdue, due-soon, and completed summaries.
Primary focus: Controlled forms, derived state, date handling, custom storage Hook, and responsive dashboard components.
2

Kanban Task Board

Create a board that organises tasks into Todo, In Progress, and Done columns. Users should be able to add detailed tasks, move them between stages, set priorities, and inspect an individual task on a separate route or dialog.

A reducer is a natural fit because each action describes a state transition: add, update, move, or remove. Drag-and-drop can be included if time permits, but accessible move buttons should remain available.

  • Support task titles, descriptions, priorities, tags, and due dates.
  • Filter the board by priority, tag, or search text.
  • Persist the board and selected filters locally.
  • Display counts and completion progress for each column.
Primary focus: useReducer, component composition, immutable updates, dialogs, and responsive column layouts.
3

Habit Tracker

Design an application for defining recurring habits and recording whether each habit was completed on a given day. The dashboard should make current progress easy to understand without turning into a complex health platform.

Calculate streaks and completion percentages from stored check-ins rather than saving those derived values separately. A weekly view provides useful date logic while keeping the project achievable.

  • Create habits with a title, category, frequency, and target.
  • Record daily completion and calculate current streaks.
  • Show weekly summaries and simple progress indicators.
  • Allow habits to be paused, edited, or archived.
Primary focus: Date-based state, derived statistics, reusable progress components, themes, and local persistence.
4

Personal Expense Tracker

Develop a private budgeting tool where users record income and expenses, assign categories, and inspect spending summaries. The application should explain where money went rather than attempting bank integration or financial advice.

Transactions can be stored locally and grouped by month and category during rendering. A small chart library is optional; Material UI progress bars and summary cards are sufficient.

  • Add, edit, and delete income or expense transactions.
  • Filter by month, category, transaction type, or search text.
  • Calculate balance, total income, total spending, and category totals.
  • Provide a monthly summary and transaction detail view.
Primary focus: Numeric form validation, array transformations, derived totals, table components, and localStorage.
5

Flashcard Learning App

Build a study tool in which users create decks and review cards one at a time. A study session should reveal answers, collect confidence ratings, and present a short result summary.

The application does not need a full spaced-repetition algorithm. A simple system that prioritises cards marked “Needs practice” is enough to demonstrate useful state transitions and local persistence.

  • Create, edit, delete, and search decks and cards.
  • Run a study session with reveal and rating actions.
  • Track recent scores and cards that need more practice.
  • Import starter decks from bundled JSON.
Primary focus: Nested routes, reducer state, conditional rendering, local data import, and session summaries.
6

Quiz Platform

Create a quiz application with categories, multiple-choice questions, a timed session, and a final results screen. Questions can come from bundled JSON so their quality and format remain consistent.

An optional extension can load questions from the Open Trivia Database, but the project should continue to function with local questions if the API is unavailable.

  • Select a category, difficulty, and quiz length.
  • Show one question at a time with progress and optional timer.
  • Review answers and explanations after submission.
  • Store personal high scores and recent attempts.
Primary focus: Multi-step state, timers and cleanup, routing, score calculation, and accessible answer controls.

Projects using public APIs

7

Recipe Explorer

Build a visual recipe application that lets users search by meal name, browse categories, and open a complete recipe. The detail screen should turn the API's ingredient fields into a clean list.

Users can save favourites and attach a private note without needing an account. Recent searches and favourites belong in localStorage; recipe content comes from TheMealDB.

  • Search recipes and browse a selected category or area.
  • Display ingredients, measurements, instructions, and images.
  • Save favourites and personal cooking notes.
  • Handle no-results, loading, network, and malformed-data states.
Data source: TheMealDB API. Primary focus: Fetching, data transformation, detail routes, and favourites.
8

Weather Dashboard

Create a dashboard where users search for a place and inspect current conditions plus a multi-day forecast. Open-Meteo's geocoding endpoint can translate a place name into coordinates before the forecast request runs.

The interface should convert weather codes into readable labels and icons. Avoid attempting advanced meteorology; concentrate on presenting a small set of useful measurements clearly.

  • Search locations and resolve duplicate place names.
  • Show current temperature, wind, precipitation, and forecast.
  • Save favourite locations and the preferred temperature unit.
  • Provide skeleton, error, retry, and no-location states.
Data source: Open-Meteo. Primary focus: Dependent requests, Effects, preferences Context, and responsive information cards.
9

Country Comparison Tool

Develop an explorer that presents key facts about countries and lets users place two or three countries side by side. The comparison should make large values understandable with formatted numbers and concise labels.

REST Countries returns nested and sometimes optional fields, providing useful practice in normalising API data before it reaches presentation components.

  • Search and filter countries by name, region, or language.
  • Show flags, capitals, currencies, languages, population, and area.
  • Compare selected countries in a responsive layout.
  • Save a shortlist of favourite countries locally.
Data source: REST Countries. Primary focus: Normalising nested data, URL parameters, comparison state, and number formatting.
10

Book Discovery App

Create a book search experience where users explore results, inspect a selected work, and maintain a personal reading list. Search results should show the information available without assuming every book has a cover or description.

Open Library results can be large and inconsistent, so this project is especially useful for pagination, fallback UI, and converting raw responses into a smaller internal model.

  • Search by title, author, or subject with pagination.
  • Display covers, publication years, authors, and editions.
  • Save books as Want to Read, Reading, or Finished.
  • Add ratings or notes that remain private in localStorage.
Data source: Open Library APIs. Primary focus: Search parameters, pagination, fallback content, custom fetch Hook, and reading-list state.
11

Pokémon Team Builder

Build a searchable Pokédex that also allows users to assemble a team of up to six Pokémon. A team summary can show shared types and total statistics without attempting to simulate battles.

Because individual details require additional requests, fetch only what the current screen needs and cache selected results in state where practical.

  • Browse or search Pokémon and open a detailed profile.
  • Display types, abilities, sprites, and base statistics.
  • Add and remove team members with a six-member limit.
  • Show a summary of team types, strengths, and stat totals.
Data source: PokéAPI. Primary focus: Paginated API data, detail fetching, shared team Context, constraints, and visual cards.
12

TV Series Tracker

Create a television discovery application where users search shows, inspect summaries and schedules, and build a private watchlist. Watched status belongs to the local application; the API only supplies programme information.

Keep episode tracking simple by marking episodes or seasons as watched. Recommendations and streaming-provider integration are outside the required scope.

  • Search shows and display useful result cards.
  • Show genres, rating, status, schedule, summary, and episodes.
  • Maintain Planning, Watching, Completed, and Dropped lists.
  • Track watched episodes and calculate series progress.
Data source: TVmaze API. Primary focus: Search, nested routes, HTML-content handling, local watch state, and progress calculations.
13

Museum Gallery

Design an online gallery for discovering artworks from the Art Institute of Chicago. Users should be able to search, open a focused artwork view, and create a personal collection.

The visual design is important, but the application should still handle missing images, unknown artists, and public-domain restrictions gracefully.

  • Search artwork and browse paginated results.
  • Show artist, date, medium, dimensions, and description.
  • Save works into named personal collections.
  • Offer a grid/list display preference and image fallbacks.
Data source: Art Institute of Chicago API. Primary focus: Search, image URLs, pagination, collection state, and accessible gallery layouts.
14

Earthquake Monitor

Build a data dashboard for recent earthquakes using the USGS GeoJSON feeds. The main view should help users understand location, time, depth, and magnitude without presenting the project as an emergency-warning service.

A map is optional. A well-designed sortable table and detail screen are enough to meet the learning objectives and avoid spending most of the project configuring mapping software.

  • Load recent earthquake data and show the feed update time.
  • Filter by magnitude, date range, depth, or search text.
  • Sort results and open an event detail page.
  • Save filter preferences and selected events locally.
Data source: USGS earthquake feeds. Primary focus: GeoJSON transformation, tables, dates, filters, and responsible data communication.
15

Currency Converter

Create a focused currency conversion tool with clearly labelled amounts, currencies, rates, and rate dates. Users should be able to reverse a pair and save combinations they use often.

The application should state that rates are informational and may not match bank rates. Historical charts can be an extension, but reliable current conversion is the core feature.

  • Select source and target currencies and enter an amount.
  • Convert values and show the rate's effective date.
  • Reverse currency pairs and save favourite pairs.
  • Maintain a small local history of recent calculations.
Data source: Frankfurter API. Primary focus: Controlled numeric inputs, request parameters, formatting, validation, and persisted preferences.
16

Public Holiday Planner

Build a planning tool that displays public holidays for a selected country and year. Users can combine those holidays with locally entered leave days to explore possible breaks.

The project should not attempt employee scheduling. Its purpose is to combine simple API data with user-created local records and clear calendar-style presentation.

  • Select a supported country and year.
  • Group holidays by month and identify the day of the week.
  • Add personal leave days and notes locally.
  • Highlight sequences that connect leave, weekends, and holidays.
Data source: Nager.Date API. Primary focus: Dates, combined remote/local data, derived ranges, and calendar-like responsive layouts.
17

GitHub Profile Explorer

Create a developer profile viewer that searches a GitHub username and presents public profile and repository information. The dashboard should emphasise useful summaries rather than reproduce GitHub.

The unauthenticated API has rate limits, so the interface must explain rate-limit errors and avoid unnecessary repeated requests. Saved profiles remain local.

  • Search a username and display the public profile.
  • List repositories with language, stars, forks, and update date.
  • Filter or sort repositories and calculate language totals.
  • Save favourite profiles and recent searches.
Data source: GitHub REST API. Primary focus: Multiple related requests, rate-limit handling, sorting, aggregation, and profile routes.

Hybrid and content-driven projects

18

Travel Packing Assistant

Develop a trip planner that generates and manages packing lists. Users enter the destination, dates, trip type, and planned activities, then begin with sensible items from bundled JSON.

An optional Open-Meteo request can show the destination forecast and suggest weather-related items. The user always remains in control of the final list.

  • Create trips with dates, destination, type, and notes.
  • Generate a starter list from bundled categories and rules.
  • Add, edit, remove, categorise, and check off items.
  • Optionally fetch weather and display relevant suggestions.
Data: Bundled packing JSON, localStorage, and optional Open-Meteo. Primary focus: Combining data sources, custom Hooks, checklists, and derived completion progress.
19

Student Portfolio Builder

Create an editor and live preview for a student portfolio. Users enter profile details, skills, education, and projects, then switch between editor and preview routes.

This extends the introductory portfolio work into React without becoming a full website generator. One carefully designed template and a few theme choices are enough.

  • Edit profile, skills, education, links, and project entries.
  • Preview changes immediately in a responsive portfolio layout.
  • Choose from a limited set of colours and typography options.
  • Save locally and export or import the portfolio data as JSON.
Data: LocalStorage with JSON import/export. Primary focus: Complex controlled forms, Context, live preview, file handling, and theme customization.
20

Accessibility Checklist Manager

Build a structured review tool based on a curated, bundled accessibility checklist. Users create a review for a website, mark checks as Pass, Fail, Not Applicable, or Not Tested, and record evidence.

This is a checklist manager rather than an automated scanner. It should support careful review of labels, keyboard access, contrast, headings, forms, and alternative text.

  • Load checklist criteria from bundled JSON grouped by topic.
  • Create reviews and record status, severity, notes, and evidence.
  • Filter findings and calculate completion and issue totals.
  • Export a review as JSON or a printable HTML report.
Data: Bundled checklist JSON and localStorage reviews. Primary focus: Accessible form design, reducer state, filtering, reporting, and print styles.

Git repository requirements

What your repository should contain

Your repository should contain everything needed to understand, install, run, and assess the project. A fresh copy should work after following the instructions in README.md.

Required project files

  • README.md with the project title, purpose, main features, setup instructions, available scripts, data source, and known limitations.
  • docs/plan.md containing the original project thinking, requirements, proposed structure, and development plan.
  • package.json and the matching lock file, normally package-lock.json.
  • src/ containing the React application source code.
  • public/ only when the project requires static files that cannot be imported from src/.
  • .gitignore configured for a Vite and Node.js project.
  • .env.example with placeholder names if environment variables are required. The real .env file must not be committed.

Source-code organisation

  • Reusable interface elements in a clear components directory.
  • Route-level screens separated from smaller reusable components.
  • Custom Hooks, Context, or reducer files separated when they contain substantial shared logic.
  • API request or storage code kept outside presentation components where practical.
  • Bundled JSON, seed data, theme configuration, and assets placed in clearly named locations.
  • Consistent file names and imports, with unused starter files removed.

Planning and evidence in docs/plan.md

Create docs/plan.md before implementation begins. Keep the initial thinking visible; if the project changes, append the decision and its reason instead of rewriting the original plan to match the finished application.

  • Initial idea: The problem, intended users, project goals, and why the idea was selected.
  • Scope: Must-have features, optional features, and features deliberately left out.
  • User journey: The main tasks a user should be able to complete from start to finish.
  • Application structure: Proposed routes, page responsibilities, reusable components, and shared state.
  • Data model: The main objects and fields, example data, relationships, and validation rules.
  • Data source: The selected public API, bundled JSON, or localStorage approach, including expected loading and error states.
  • Interface plan: Early sketches or wireframes, responsive layout decisions, and planned Material UI components.
  • Accessibility plan: Keyboard use, labels, headings, colour contrast, alternative text, and validation feedback.
  • Testing plan: Important user journeys, edge cases, and logic that must be checked.
  • Task breakdown: A realistic order of work for the available development time.
  • Changes during development: Decisions that differed from the initial plan, with a short explanation of why.
  • Completion evidence: Desktop and mobile screenshots plus a short comparison between the plan and final result.

Git history

  • Regular, meaningful commits that show the project developing over time.
  • Commit messages that describe the change, such as “Add recipe search states” rather than “update”.
  • A working final version on the repository's default branch.
  • No generated dependency folders, secrets, unrelated files, or large unused assets in the history.

Do not commit

  • node_modules/, build output such as dist/, or temporary cache folders.
  • .env files, API keys, access tokens, passwords, or other private information.
  • Editor, operating-system, or temporary files that are unrelated to the project.
  • Large media files that are unused or can be replaced by appropriately sized web assets.

Final repository check

  • A fresh clone can run with npm install followed by npm run dev.
  • The production build completes with npm run build.
  • The application contains no broken imports, missing assets, broken routes, or avoidable console errors.
  • The README accurately describes the submitted version of the application.

Assessment criteria

How your project will be assessed

All project choices use the same criteria. Assessment focuses on the quality of the implementation and your understanding of the submitted work.

  • 20% — Planning and structure: The initial thinking and decisions recorded in docs/plan.md, including requirements, routes, components, and data model.
  • 25% — React implementation: State, events, Hooks, component reuse, and immutable updates.
  • 15% — Data handling: Fetching or local persistence, transformation, and edge states.
  • 15% — Interface quality: Responsive Material UI design and coherent theme.
  • 15% — Accessibility and reliability: Labels, keyboard use, semantic structure, validation, and errors.
  • 10% — Explanation: README, setup instructions, known limitations, and ability to explain key code.
